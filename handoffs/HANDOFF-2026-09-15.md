## 1. What it is

`AMD-NR-ReShade-Installer` is the graphical manager for the add-on
[dlss5-neural-amd](https://github.com/zmodelerlover/dlss5-neural-amd), which runs the DLSS 5 Neural
Rendering network on Radeon cards through ReShade.

It solves the two things the terminal installer did not:

- the files came from the Discord `files` channel, and finding that was where most people got stuck;
- it was a terminal: it did not show a library, did not detect the GPU, did not warn about a new version.

Today it **installs everything by itself, with no third-party window**: add-on, runtime, weights, the
32-bit bridge pair and **ReShade itself**.

- Repository: `D:\AMD-NR-ReShade-Installer` (git, branch `master`, still **not published**).
- Published executable: `D:\AMD-NR-ReShade-Installer\dist\AMD-NR-ReShade-Installer.exe`
  (~48 MB, self-contained, does not need .NET installed).
- User data: `%AppData%\AmdNrInstaller\` (`cache\`, `logs\`, `games.json`, `settings.json`).

## 2. Decisions already made (do not reopen without a new reason)

| Decision | Why |
|---|---|
| **Everything in C#**, port of the Rust engine | The user's choice. The Rust (`installer/` in the other repo) still exists and was not touched. |
| .NET 10 + Avalonia 11.3.12, no MVVM framework | Same stack as Optiscaler-Client, which is the UX reference. |
| **Update = check and notify**, never auto-replace | Optiscaler-Client removed auto-update on 2026-08-18: with `PublishSingleFile` Windows locks the exe and the app came back running the old build. |
| Payloads in a **Hugging Face dataset** | The files cannot be on GitHub, and the user **swaps payloads often**. HF is the only free host whose address is both **stable and overwritable**: `https://huggingface.co/datasets/<user>/<repo>/resolve/main/<file>` stays the same after uploading a new build. So swapping a payload never again requires a new app build. Reading is anonymous (public repo, the app sends no token), it serves `Range` (checked: `206` on a 548 MB LFS file), and it is made for model weights — 141 MB is nothing there. Account needs only an e-mail, no card. |
| **catbox.moe becomes a mirror** | It was the first destination (upload with no account at all, the most anonymous option there is) and it works: the 9 files were checked byte for byte from there. But a catbox address is **immutable** — new payload = new URL = new `config.json` = new build. A cost that does not pay off. It stays as a second address, free, and nothing is trusted beyond the hash. |
| `mirrors[]` per file | Extra addresses per file, tried in order. Swapping or adding a host becomes a manifest edit, not a new build. |
| **Distributed API database** (`payload/api-db.json`), not a live query | Measured: after ~40 queries PCGamingWiki's Cloudflare started answering **403 to .NET** while curl from the same IP got through. Live queries from each user's PC would not work at scale. |
| **ReShade extracted from the official installer**, not executed | ReShade's `.exe` is an appended zip. Extracting gives a silent install, with backup and uninstall through the same transactional engine. Running the setup hidden gives none of that. |
| Optiscaler-Client code is **not reused** | It is GPL-3.0, this repo is MIT. Only the *method* was copied (which registry keys to scan, `Binaries\Win64`, DLL fingerprints). |

## 3. Architecture

```
src/AmdNr.Core/     net10.0-windows, no external dependencies
  Engine.cs         hashes, PE, INI, ownership, paths, MoveFileEx write-through
  Manifest.cs       the install manifest (format byte-for-byte compatible with the C++/Rust one)
  Transaction.cs    guard + apply + uninstall (journal, backup, rollback)
  X86Installer.cs   32-bit route (bridge)
  Work.cs           presets, Report, preflight, install, uninstall, detect
  Graphics.cs       which API the game uses: exe imports, engine, fingerprints
  Pcgw.cs           parser for the PCGamingWiki {{API}} template + title normalization
  ApiDatabase.cs    api-db.json: reading, lookup by appid and by title
  Scanning.cs       Steam/Epic/GOG/EA/Ubisoft/Battle.net/Xbox
  PayloadManifest / PayloadCache / CoverCache   download, extraction, verification, staging

src/AmdNr.App/      net10.0-windows, Avalonia, single-file self-contained win-x64
tests/AmdNr.Core.Tests/   117 tests
tools/ApiDbBuilder/       generates payload/api-db.json from PCGamingWiki
tools/seed-cache.ps1      fills the cache from local files (offline / testing)
payload/payload.json      what to download, from where, and which hash
payload/api-db.json       840 games: which APIs each one supports
```

The engine was ported from `installer/src/engine.rs` and `installer/src/work.rs` in the other repository.
**Behavior is a contract**: the refusal sentences are asserted by tests, and the install manifest
has to stay byte-for-byte identical to what the C++ installer wrote, otherwise every already
existing installation becomes "Modified or unsupported install manifest".

## 7. Traps already paid for (do not repeat)

- **Cloudflare blocks .NET's HttpClient by TLS fingerprint.** Headers and HTTP version do not
  change anything; Windows curl gets through. That is why `ApiDbBuilder` calls `curl.exe` as a process, and
  why the database is distributed instead of queried.
- **`ZipArchive` does not open a zip appended to an exe**: the offsets count from the start of the zip. Find the EOCD and
  rebase (`PayloadCache.OpenAppendedZip`).
- **Template field regex**: `\s*` swallows the line break, so an empty field steals the
  next line as its value. That is how Metro 2033 "supported" Vulkan and OpenGL. Use `[ \t]*`.
- **The file name does not say what the DLL is.** God of War's `dxgi.dll` here is OptiScaler. Read
  the version resource before saying "ReShade found".
- **Unreal game**: the add-on goes in `<Project>\Binaries\Win64`, not in the root — the root only has the stub.
- **Game with a Roman numeral in its name**: "Grand Theft Auto V" → `GTA5.exe`. The exe choice
  normalizes Roman numerals to digits, and excludes `*LanguageSelect*`, `*trial*`, crash handlers etc.
- **`$Home` is a reserved PowerShell variable**; and a `[string]$X` parameter converts an object to a
  string silently (that is how `seed-cache.ps1` "found no component at all").
- **Python heredoc with `\a`, `\n`, `\\`** breaks C# paths and strings. Prefer direct editing.
- **The 32-bit route does not install `addon64`** and reads the payloads from both `files\` and the root of
  staging.

## 10. What changed on 2026-09-15 (second pass)

### Reported bug: Uninstall did not clear "Installed"

Root cause in `Scanning.cs`. `IsInstalled` answered based on the **existence of the manifest**:

```csharp
File.Exists(.../dlss5-neural.install.json) || File.Exists(.../dlss5-x86bridge.install.json) || ...
```

But `Transaction.Uninstall` **keeps the manifest on purpose** whenever it preserves a
configuration entry — and a 64-bit install **always** writes `ReShade.ini` as an owned+config entry.
So every successful uninstall left the manifest, and the badge never cleared. The files were
removed correctly all along; what lied was the reading of the state.

Now the state comes from the payloads on disk (`Work.InstalledMarkers`), which is exactly the set that
uninstall removes. Proven at both levels: the tests fail against the old code, and the headless UI
shows `badge=True -> False` with `manifesto=True` on both sides.

### First run

`SetupWindow` — a separate window, 4 steps: language, this machine (GPU + HIP 7), files (checks the
hash of each component and downloads what is missing), your games (scan). It writes to `settings.json`,
`games.json` and the cache, which is what the main window already reads, so it returns nothing beyond
"reached the end". Closing via the X does **not** mark `SetupDone`, and on the next launch it asks again.
`App.OnFrameworkInitializationCompleted` switches `ShutdownMode` while the wizard is open, otherwise the
process would die when it closed (there is no MainWindow yet).

### Logo

`Assets/logo.png` (a square, centered crop of the user's PNG, which has alpha) and `Assets/app.ico`
(16 to 256, generated from it). The background tile became **white** (`LogoFill`) because the logo is red:
red on red does not read at 40px. Two places use it: the rail and the "About" card in Settings.

### UI bugs found in the headless render

1. `Border.iconTile.ok > PathIcon` was a **direct child** selector, and the tiles that also show a
   spinner wrap the icon in a `Panel`. Result: the background turned green, the icon stayed white.
   It affected the sheet's result banner and the "Files" step. It became a descendant selector.
2. Component size with integer division: everything under 1 MB showed up as "0 MB".
3. The "About" card had the "NR" as text and ended up as an empty white square after the logo swap.

### Core bugs found in review

4. **Three `async void` without `catch`** (`OnInstall`, `OnUninstall`, `OnScan`). The engine wraps what it
   anticipates in `InstallException`, but anything that escaped killed the window in the middle of an install. Now it becomes
   a report line (`Failure(ex)`) and goes to the log.
5. **`ScanAll` only handled three exception types per source.** A `.vdf`/registry in an unexpected format became an
   `AggregateException` from `Parallel.ForEach` and brought the app down. Now a source that fails costs its
   games, never the scan or the window.
6. **32-bit uninstall without a manifest gave a red error** ("No install manifest") for the normal
   situation of a folder where nothing was installed. The 64-bit one always scanned by name in that case. Now both
   do the same.
7. **`Pins()` without a manifest falls back to `AddonSize = 0`**, and preflight compared the right file
   against that zero: *"... is 550400 bytes, and this release expects 0. That is a different build"*.
   Unknown size is now not compared.

### Hosting

Two passes. First catbox.moe (upload with no account, as anonymous as possible): the 9 files, plus
`payload.json` and `api-db.json`, were uploaded, downloaded back and checked against the pinned hash.
It works — but a catbox address is **immutable**, and the user swaps payloads often, so
every swap would cost a new app build.

Final destination: **Hugging Face dataset**, stable and overwritable address. `tools\publish-payload.ps1`
does the migration and every future swap in one command: uploads what changed, recomputes size and SHA-256 from the
local bytes, **bumps the version of the component that changed** (the cache is `<component>/<version>`, and
new bytes under the same version read as a corrupted cache), rewrites and uploads `payload.json`, and then
downloads everything back to check. `-Verify` alone only checks. The catbox addresses stay as
`mirrors`.

`dlss5-neural-host64.exe` is on catbox under a `.bin` address because catbox refuses `.exe` — it does not
cost anything, because `name` is the name on disk and `url` is only where the bytes come from. On HF this is not
necessary.

**Published at `zmodelerlover/amd-nr`** (public dataset). The 8 files plus the two manifests,
all downloaded back and rechecked. The mirror fallback was actually exercised: a dead
primary address falls back to the catbox mirror and passes the hash, and a mirror with different bytes is refused.
End-to-end proof with a cleared cache: the app's own code downloaded everything from the stable address and
assembled the staging for both routes; `api-db` with 840 games.

**The write token used for publishing was pasted into the chat — revoke it at
huggingface.co/settings/tokens.** The login is already saved in `~/.cache/huggingface/`, so revoking
breaks nothing until the next publish, which will ask for `hf auth login` again.

### Tests

120 green (there were 117). The new ones: a preserved manifest is not an install; x64 round-trip with ReShade
clears the badge; x86 uninstall without a manifest scans instead of failing; unknown size does not become
"different build".

### Headless harness

Still disposable, in `%TEMP%\ui-headless\` — `Avalonia.Headless` + `Avalonia.Skia` 11.3.12,

## 11. Third pass: emulators, Play, per-install log

### Emulators are now a path, not just a route

`src/AmdNr.Core/Emulators.cs` — a table of 14 emulators: how to recognize them (exe names), which route,
which renderers, and **the sentence that names the setting that actually decides**. An "Emulator…" button in
the bar: picks PCSX2, RPCS3 or "other", and then asks for the folder of *that* emulator. What is in the folder
wins — someone who picks PCSX2 and points at RPCS3 gets RPCS3, not a silently wrong route.

**Core bug this dug up:** `GuessPreset` got PCSX2/RPCS3 right, and `DetectAllAsync`
**overwrote** it with `Dx11` right afterwards, because detection did not know what an emulator was and an emulator's exe
imports every renderer at once. The emulator route never survived.
Now `Emulators.Identify` is signal 0 of detection, before any import reading, and
`GuessPreset`/`ExpectedExe`/`CheckExe` read the same table — they can no longer disagree.

`CheckExe` also accepts any build name of the same emulator (PCSX2 ships under five).

### Play / Open in the sheet

Steam goes through `steam://rungameid/<appid>` — it is the path the game expects (its own launcher, DRM,
overlay); running the exe directly breaks that. Without an appid, the executable that detection already found. The label
becomes "Open" when it is an emulator, and the button is disabled when there is nothing to open.

### Per-install log

`%AppData%\AmdNrInstaller\logs\<date>-<action>-<game>.log`, one per install/uninstall, keeping the 100
newest. It carries what a bug report needs and the on-screen report does not have: machine (GPU,
driver, HIP 7), target and route **and who chose the route**, the detection evidence, versions and hashes
of the payloads, the whole report, and the folder afterwards — with each DLL identified by its version
resource, not by its name (`dxgi.dll [ReShade 6.8.0]`).

### Half-Life: why ReShade did not open

It was not the installer. The `d3d9.dll` in the folder has a hash identical to the pinned ReShade32 — it was installed
correctly. What happens is that Half-Life's `hw.dll` imports **only `OPENGL32.dll`**: the current Steam
build has no Direct3D renderer at all, so nothing ever loads that `d3d9.dll`.

Detection from the files gets it right on its own (it says OpenGL, no route). What forced D3D9 was
`api-db`: PCGamingWiki lists D3D9 (true for the pre-anniversary build) and `With(wiki)` **replaces**
what the files say. It did not become an exception list — the project refuses whitelists. It became
`CheckRouteIsReachable`: when the route asks for a renderer that this copy's files do not link,
preflight warns, with the evidence. Half-Life now says:

> This route needs DX9, and the files here link OpenGL instead. hl.exe loads hw.dll, which imports
> opengl32.dll.

**Half-Life cannot work on this build.** The warning is the product, not a fix.

### One more core bug, found in the same output

`CheckReShade` only looked for 64-bit names (`d3d11/dxgi/d3d12`). On the 32-bit D3D9/D3D8 route ReShade
goes in as `d3d9.dll`, so **every** 32-bit install got "No ReShade proxy DLL found here"
with ReShade right there in the folder — including the ones the app itself had just written. The names
now follow the route.

every name it uses; an emulator keeps its route against the imports (with the same bytes in two folders
proving the contrast); an emulator without its own preset routes through the best renderer; preflight accepts
any build name; and the ReShade proxy follows the route.

ReShade log proves the whole chain:

```
Searching for add-ons (*.addon, *.addon32) in '...\half-life 2in' ...
Loading add-on from '...\half-life 2in\dlss5-neural.addon32' ...
Registered add-on "dlss5 neural x86 bridge" v0.0.0.0 using ReShade API version 20
```


Reported as "installing on Half-Life 2 didn't work". The installation was **correct** and in the wrong
place. The per-install log delivered it on the first try: route `X86Dx9`, `d3d9.dll [ReShade 6.8.0]`, everything
checked — in the root.

Reading the binaries:

| module | arch | imports |
|---|---|---|
| `hl2.exe` (root) | x86 | **no graphics at all** — stub |
| `bin\shaderapidx9.dll` | x86 | **`d3d9.dll`** |
| `bin\shaderapivk.dll` | x86 | `DXVK_D3D9.DLL` |

Source loads the modules from `bin\` with `LOAD_WITH_ALTERED_SEARCH_PATH`, so their dependencies
resolve from `bin\` and **the root is never consulted**. Proven in two steps: with
ReShade only in the root there was no `ReShade.log` anywhere; copied to `bin\`, it loaded and
logged `Searching for add-ons (*.addon, *.addon32) in '...\Half-Life 2\bin'` — the add-on was still in the
root, and that is why the tab did not appear.

**The fix separates two concepts that were glued together:** `GraphicsDetection.Executable` is what gets
opened (still `hl2.exe`), and the new `InstallTarget` is the file whose folder receives the files
(`bin\shaderapidx9.dll`). `Target` returns one or the other; `TargetFor` and `RefreshInstalled` use
`Target`. An ordinary game has a null `InstallTarget` and nothing changes for it.

Note: Source's "Vulkan" backend is DXVK translating D3D9, so the D3D9 route serves both.

It is the same shape as Unreal (`Binaries\Win64`), which was already handled — but through a different path
(`FindExecutable` found the right exe). Source could not be solved that way, because the right exe is
in the root and the files are not.

## 12. Roadmap

### Choosing the release/version per game, in the sheet

Today the version is global: `payload.json` gives **one** `version` per component and every game installs
that one. The request is that, when clicking on the game, the person chooses which release they want — **from 0.5
onward** (nothing earlier goes into the list).

It serves two things that have already happened in this project: testing a new runtime on a single game without
touching the others, and taking a game back to the previous version when the new one regresses on it.

**What this touches, in order of difficulty:**

1. **`payload/payload.json`** — today `components.<name>.version` is a string. It becomes a list of
   versions, each with its own `files` (url, size, sha256). The `schema` goes from 1 to 2, and
   `PayloadManifest.Parse` has to keep accepting schema 1 — otherwise every exe already distributed
   stops reading the manifest on the next publish.
2. **`GameEntry`** (`src/AmdNr.App/Services.cs`) — gains something like `PayloadVersion`, null = "the
   newest". Same pattern as `PresetChosen`: once chosen by hand, a manifest update no longer
   overwrites it.
3. **The sheet** (`MainWindow.axaml`) — a combo next to the Route one. It only appears when more than one
   version is offered.
4. **`PayloadManifest.Pins()`** — today returns the hashes of the single version. It starts taking which one.
5. **`tools/publish-payload.ps1`** — instead of overwriting the version, it appends an entry to the
   list. This changes `-SetVersion` and the auto-bump.

**What does NOT need to change, and is what makes this cheap:** the cache is already
`cache\<component>\<version>\` and staging is already `<component>.<version>-...`, so two versions
coexist on disk with no new work. `Transaction` already records in the game's manifest what was
installed, and preflight already checks hash by hash.

**Trap not to repeat:** the Hugging Face address is stable *per file name*. Publishing
a 0.6 without changing the name overwrites 0.5 and the list starts lying. Versions that coexist need
names that coexist — `dlssnr_amd_pass1-0.2.18.dll`, not `dlssnr_amd_pass1.dll` again.

### Open: two bugs in the 32-bit route's `dlss5-neural.ini`

Found while checking the hotkey against the add-on binary, not fixed.

1. **`Engine.FreshIni()` writes `ColourStrength=0.25`, and that key does not exist in the add-on.** Zero
   occurrences in the binary, neither as an ini line nor as a substring; `ColorStrength` also zero.
   It is not a spelling variant, it is a dead setting. The other four (`Scale`, `Passes`, `Structure`,
   `Skin`) exist.
2. **The pre-written ini swallows the add-on's documented template.** The add-on only writes its own
   *"because no dlss5-neural.ini was here"*; the 32-bit route writes one first, so the file that
   remains has no `StartOn`, no `ToggleKey`, no `ToggleMods`, nor the block that explains the key
   codes. And the installer itself tells people to set `StartOn=1` in that file — which on a 32-bit install
   does not have that line. The hotkey keeps working (Ctrl+End comes from the compiled default); what is
   lost is discovering it and changing it through the documented path. The 64-bit route does not write the ini and does not
   have the problem.

The hotkey itself is right: the add-on defines `ToggleKey=35` (0x23 = VK_END) and `ToggleMods=1` (Ctrl),
so **Ctrl+End** and `StartOn=1` match what the installer says.

Proposed fix: stop pre-writing the ini on the 32-bit route and remove `ColourStrength`. Check
first in the original Rust (`git -C D:\dlss5 show origin/master:installer/src/work.rs`) whether there was a reason
for these values — `Scale=1.0` and `Passes=1` are identical to the add-on's defaults, so the only
real "overrides" today would be `Structure=1` and `Skin=1`, if they differ at all.


### Hotkey: diagnosed — the ini is read, the overlay does not save

Reported by the user, **not reproduced and not diagnosed**. It stays here with what is already known, so that
the investigation does not start from zero.

What was checked on 2026-09-15, on Half-Life 2 (32-bit route, installed in `bin\`):

| | |
|---|---|
| `Half-Life 2\dlss5-neural.ini` | 147 bytes, 04:01:59 — no `ToggleKey`/`ToggleMods`/`StartOn` |
| `Half-Life 2\bin\dlss5-neural.ini` | 147 bytes, 04:06:10 — same |
| attributes | `A` on both; neither is read-only |

147 bytes is exactly what `Engine.FreshIni()` writes. In other words: **neither of the two has been written by the
add-on so far.** The add-on's overlay saves to `dlss5-neural.ini` and nothing arrived there.

**RESOLVED on 2026-09-15, with the add-on running in Half-Life 2.** Two halves, and only one is broken.

**The ini is read.** Writing `ToggleKey=120` and `ToggleMods=1` by hand in `bin\dlss5-neural.ini` and
restarting the game, the bridge log confirms it picked them up:

```
x86bridge native x86 protocol=2 mode=NEURAL StartOn=0 ToggleKey=120 ToggleMods=1 probe=off
```

That log is the diagnostic tool: **the add-on prints the bind in use at startup**, so you can
know what it is running without seeing the screen.

**The overlay does not save.** A scan of the whole HL2 tree during a 5-minute session with the
add-on loaded and registered: no `dlss5-neural.ini` was written, neither in `bin\` nor in the root. The
add-on created its logs and nothing else. The panel's Save does not persist the key.

**Therefore:** you can change the hotkey by editing the file; you cannot through the panel. It is an add-on bug
(other repository), not an installer bug.

**What is still unknown:** whether the key capture in the panel does not register the combination, or whether it
registers it and it is the Save that does not write. From outside the two cannot be separated.

**Context that may matter to whoever tackles this:**

- The game was in **exclusive fullscreen** (`Windowed | FALSE` in ReShade.log). Cheap and
  obvious test: repeat it windowed. If capture works windowed, it is an input problem in exclusive mode.
- Source uses SDL2 and creates a separate window just for input (`SDLHelperWindowInputCatcher` shows up in
  ReShade.log). If the add-on reads the keyboard through a path tied to the render window, it may never see the
  key. The ReShade overlay itself responds normally, so ReShade's path works.
- ReShade installs hooks in `dinput.dll` and `dinput8.dll`.

**Trap when testing:** do not use **F10**. On Windows F10 generates `WM_SYSKEYDOWN`, not `WM_KEYDOWN`, and
a handler that only listens to `WM_KEYDOWN` never fires — a false negative that has nothing to do with the
bug. Use F9 (120) or Insert (45).

### Report collector bug, found during this diagnosis

`SupportReport.RuntimeEvidence` looked for `dlss5-neural.log`. The 32-bit route does not use that name: it
writes `dlss5-neural-x86.log` (the frontend) and `dlss5-neural-x86-host.log` (the 64-bit helper). The support
zip was leaving out exactly the two files that gave the answer about the hotkey.
Fixed; all three names are included now.

### The hotkey bug was in the add-on, and it was tackled there

Investigated down to the root cause and fixed in `dlss5-neural-amd`, **not** in this repository. Its own
handoff: `D:\dlss5-hotkey\HANDOFF-x86-hotkey-2026-09-15.md` (copy on the Desktop), branch
`fix/x86-hotkey-capture`, branching from `origin/master`. Nothing committed or pushed.

Summary: there were two defects. The loop that scans the keys lived in the overlay's draw callback, which
went **672 ms** without being called, while the cancellation lived in the Present path, which runs every
frame — the cancellation always won and the scan never ran once. With that fixed, the capture started
picking up the `Home` key that opens the overlay itself, still held down. Fixed with a wait for release.
Still needs validation in game.

For this repository only one thing matters: **the installation was never at fault.** The ini is read
from the right folder, the add-on loads, the route is correct.
