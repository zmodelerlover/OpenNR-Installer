# Handoff — v0.2.0: installing into OpenGL games, and the payload that almost shipped broken

2026-09-20. Everything pushed and published: installer `v0.2.0`, add-on `v0.6.0`, payload with the
`addon` at 0.6.0. Read after [HANDOFF-2026-09-15.md](HANDOFF-2026-09-15.md), which is still
the complete description of the app; this file covers only what changed and what went wrong.

---

## 1. What went in

The add-on gained an OpenGL route, so the installer gained a way to install it.

| | |
|---|---|
| `Preset.OpenGL` | x64 route, placed **after** Vulkan in the preference order |
| Proxy | `opengl32.dll`, with `dinput8.dll` as the alternative |
| Detection | `(X64, GraphicsApi.OpenGL) → Preset.OpenGL`; 32-bit still has no route |
| Manifest | `"OpenGL"` accepted in `Manifest.Decode` |
| Emulators | xemu is no longer a dead end; melonDS gets a renderer instruction; Azahar keeps Vulkan as the recommendation |

The proxy name was not guessed. The list of names in `Work.ProxyChoicesFor` says, in its own
comment, that they are the names whose entry points the pinned ReShade actually exports — so I read the
exports of the pinned `ReShade64.dll`: 24 `wgl*` entries plus the GL 1.1 set. `opengl32.dll` passes
the same criterion that `dxgi.dll` and `dinput8.dll` passed.

Validated outside the fixtures: pointing `GraphicsDetector.Detect` at the real Luanti folder, the
answer is `luanti.exe imports opengl32.dll → api OpenGL → preset OpenGL → opengl32.dll`.

### The bug the test caught before the user did

`Manifest.Decode` validates the route name against a closed list, and `"OpenGL"` was not in it. The
installation would have **written** the manifest and the next read would reject it — taking the folder's
state and the uninstall down with it. It is the kind of defect that only shows up after writing to
someone's disk. Adding a name there is backward compatible: an old manifest still decodes, and an
old build rejects a new manifest, which is the honest answer, because it would have no route to
uninstall.

## 2. The payload incident — read before publishing anything

**The two copies of `payload.json` were out of sync.** The one in this repository
(`payload/payload.json`) still pinned the `bridge` at **v0.5.2**, while the files published
under those names are the **v0.5.3** pair. The mirrored copy in the `AMD-NR-Extras` repository was
correct. Nobody had any way to notice, and the reason is item 3 below.

Publishing from this repository's copy, the old bridge hashes went into the live
manifest. For a few minutes, **an installation into a 32-bit game would have been rejected at the
hash check** — the app does exactly what it should, and it was the manifest that was wrong.

Fixed by taking the pins from `extras` (which are those of the files actually published), republishing
and running the full verification, which now passes on all nine files. The two copies are
identical and committed.

**The rule that stays:** before publishing, compare `payload/payload.json` with the one in `AMD-NR-Extras`.
If they diverge, find out which one describes what is in the dataset **before** uploading — `publish-payload.ps1
-Verify` answers that without writing anything.

## 3. Why the script let this through

`tools/publish-payload.ps1` died **between uploading the manifest and verifying it** — the worst
possible place: everything live, nothing checked. Cause: `hf` writes warnings to stderr (`Removing 1 file(s)
from commit that have not changed`) and, under `ErrorActionPreference = 'Stop'`, a redirected stderr
line becomes a terminating error in Windows PowerShell.

Now all calls go through `Invoke-Hf`, which relaxes the preference during the call and leaves
the verdict to the exit code — which all callers were already testing. Step 7 of the script (download
everything back and check hashes) runs again, and it was what caught the problem in item 2.

Two pitfalls found while writing this, both in the code comment:

- the function **cannot** be named `Hf`: PowerShell is case-insensitive, the name shadows the
  `hf` executable and the call from inside re-enters the function;
- running the script from Git Bash scrambles `PSModulePath`, and then cmdlets like `Get-FileHash` disappear.
  Run it from PowerShell. This is not a bug in the script — I went as far as "fixing" it based on that
  wrong diagnosis and reverted it.

## 4. Published state

| | version | where |
|---|---|---|
| Installer | `v0.2.0` | release with `AMD-NR-ReShade-Installer.exe` + `SHA256SUMS.txt` |
| Add-on | `v0.6.0` | release with `dlss5-neural.addon64` + `SHA256SUMS.txt` |
| Payload | `addon` 0.6.0, `runtime` 0.3.0, `reshade` 6.8.0, `bridge` 0.5.3, `x86-extras` 1 | dataset `zmodelerlover/amd-nr` |

`publish-payload.ps1 -Verify` passes on all nine files.

**Auto-update was tested by the user after publishing and it worked** — 0.1.1 replaced itself
with 0.2.0 on its own. It was the path that had never been exercised end to end: the release
publishes the `.exe` + `SHA256SUMS.txt` pair, the app downloads it, checks the hash against the sums from the same
release, moves the running executable to `.old`, puts the new one in place and restarts.

Publishing order, which matters: **installer first, payload after**. `payload.json` is read
at runtime by every installer already installed, so the moment the new add-on
enters the manifest, anyone on the old version starts downloading it — it works on the routes that
version knows, but it does not offer the OpenGL one.

## 5. What was left out

- `GameScanner.GuessPreset` still guesses `Dx11` before detection runs. It is old and
  harmless behavior — detection overwrites it right after, and the card settles on OpenGL by itself —
  but it duplicates knowledge that already exists in `GraphicsDetection.RouteFor`.
- The script rewrites `src/AmdNr.App/config.json` with a BOM and its own indentation on every publish,
  without changing content. `File.ReadAllText` swallows the BOM, so it is just diff noise; it was reverted by
  hand in this publish.
- Nothing in the app says a route is experimental beyond the text of the note. The OpenGL one is the newest of
  all.
