# Handoff v0.4.0: OptiScaler route for D3D12 games

2026-09-23. Read after [HANDOFF-2026-09-20.md](HANDOFF-2026-09-20.md). This file covers only the
new route.

---

## 1. What went in

On D3D12 the ReShade add-on only sees the finished frame. A D3D12 game with DLSS, FSR or XeSS has a
better path: the OptiScaler fork
[neural-amd-opti](https://github.com/MatheusFerreiraS/neural-amd-opti), which takes over the game's
upscaler call and runs the same network inside it, with the game's own depth and motion
vectors. The installer now installs that fork as one more route.

| | |
|---|---|
| `Preset.OptiScaler` | x64 route, manifest `"OptiScaler"`, last value of the enum (the old `games.json` still reads) |
| Recommendation | `GraphicsDetection.Preset`: a game whose best route would be D3D12, or that runs D3D11 and D3D12 and ships an upscaler, gets OptiScaler. `Recommended` becomes D3D12, so a game with both hears "switch to DX12" |
| Upscaler | `GraphicsDetector.Upscalers`: DLSS, FSR or XeSS next to the exe, at the root and, on Unreal, in `Plugins\` and `Engine\Plugins\` (one pass per tree) |
| Proxy | `dxgi.dll` or `winmm.dll` (`Work.ProxyChoicesFor`) |
| Code | `src/AmdNr.Core/Work.OptiScaler.cs`: preflight, install and what is left after uninstall |

No ReShade route went away. The two share the x64 manifest, and that is what makes them
alternatives: `Transaction.Apply` rejects a second preset in the same folder.

### What goes into the game folder

`OptiScaler.dll` under the proxy name, `OptiScaler.ini`, `OptiScaler\` (FidelityFX, XeSS, XeLL),
`OptiScaler\D3D12_OptiScaler\D3D12Core.dll`, `experimental_lighting\`, runtime **0.3.1** as
`dlssnr_amd_pass1.dll`, `pass2` and `pass3` (OptiScaler loads one module per pass) and the same
weights as the add-on. All names are in `Engine.Allowed`; `OptiScaler.ini` is configuration
(`Engine.IsConfig`), preserved on uninstall like `ReShade.ini`, and an `OptiScaler.ini` that was already
in the folder and is not ours is not overwritten.

### Decisions that are not obvious

- **The runtime is not the add-on's.** The payload's `runtime` is a 0.3.0 with hash `70af3fb7…`, which
  OptiScaler does not recognize (it identifies the runtime by SHA-256 and uses fixed offsets). The route uses
  danielblnc's original 0.3.1 (`b108d640…`), in its own component. The weights are the same
  (`6bf8dc93…`), so they come from `runtime`.
- **`D3D12Core.dll` lives in `D3D12_OptiScaler/` in the cache.** `PayloadManifest.Parse` rejects paths with
  more than two levels, and every app already distributed validates all components, including the ones it does not
  know. A three-level path would make the manifest unreadable for everyone. `Work.OptiDestination`
  puts the file in the right place at install time.
- **Uninstall without a manifest on the OptiScaler route removes nothing.** The name-based sweep of the x64 route removes
  `dlssnr_amd_pass1-10.dll` and the weights; in a folder with an OptiScaler installed by other means (the
  fork package's `Setup.bat`) that would break the installation. It says which uninstaller to use.
- **A manifest left over from a ReShade uninstall is adopted.** The ReShade uninstall keeps the
  manifest when it preserves `ReShade.ini`, and `Apply` would refuse to switch presets on top of it
  forever. `AdoptLeftoverManifest` switches the preset when only configuration entries remain.
- **`PayloadMovedOn` looks at the preset.** Compared with the add-on's pins, `dlssnr_amd_pass1.dll` from an
  OptiScaler installation would always look outdated. `PinnedForOptiScaler` compares with the route's.
- **On-demand download.** `PayloadManifest.OnDemand` and `Everyday`: OptiScaler's 132 MB stay out
  of the wizard, the "This machine" tab and "download everything". They only come down when someone installs the route.

## 2. Payload

Two new components in `payload.json`:

| component | version | from where |
|---|---|---|
| `optiscaler` | `0.1.1-amd-nr` | the neural-amd-opti release zip on GitHub, with `extract` listing the 14 files and the hash of each one |
| `opti-runtime` | `0.3.1` | `dlssnr_amd_runtime-0.3.1.dll` in the HF dataset |

**Backward compatibility:** the new manifest is still schema 1, with paths of at most two
levels, so an old app reads it. But an old app's wizard downloads **all** components,
the 132 MB included. That is why the order is still installer first, payload after.

### Coupling with neural-amd-opti: read before publishing a new OptiScaler

The payload pins the release zip **and** each file extracted from it. A new release of the fork is:

1. an `optiscaler` component with a new version (the cache is `<component>/<version>`);
2. the URL of the new release zip;
3. the `extract` hashes recomputed from that zip.

`publish-payload.ps1` does not do step 3: it only uploads files to HF and leaves alone anything with a URL
on another host. Compute the zip's pins (name, path, size, SHA-256 of each entry) and edit
`payload.json` before running the script. **Never re-upload an asset with the same name under the same tag** of the
fork: the address does not change and every app starts rejecting the file by hash.

## 3. Evidence

- 188 green tests (there were 178). The new ones are in `tests/AmdNr.Core.Tests/OptiScalerRouteTests.cs`:
  recommendation (D3D12, D3D11+D3D12 with and without an Unreal upscaler), install in the right places, `winmm.dll`,
  uninstall that restores and cleans folders, user ini preserved, installed ReShade route rejected,
  leftover manifest adopted, outdated by preset and on-demand components.
- End to end with the real files, using the app's own code: downloaded the zip from GitHub and the
  runtime from HF, checked each extraction by hash, assembled the staging, installed into a throwaway folder and
  uninstalled.
- Installed through the window in Cyberpunk 2077 by the user, on 2026-09-23, and working in game.

## 4. What was left out

- A **D3D11-only** game with DLSS still recommends ReShade D3D11, which is the route where the add-on receives
  depth and motion. OptiScaler also runs there, through its D3D12 bridges, but it was not tested.
- The route has no OptiScaler version selector. The "Add-on version" section disappears on it.
- OptiScaler installs with NR turned off (it is the package's `OptiScaler.ini`). The report and the route's
  note say how to turn it on.

## 5. Release: the exe alone is not enough

Without `config.json`, `payload.json` and `api-db.json` in the same folder, the installer does not work. Every
release carries, besides the two loose files, an archive with the whole folder:

| asset | what for |
|---|---|
| `AMD-NR-ReShade-Installer.exe` | the auto-updater downloads this one (`Services.ExeAsset`); it cannot be left out of the release |
| `SHA256SUMS.txt` | the hash the updater checks (`Services.SumsAsset`) |
| `AMD-NR-ReShade-Installer-vX.Y.Z.7z` | what the person downloads the first time: a folder with the exe, `config.json`, `payload.json` and `api-db.json` |

`dotnet publish` already puts the three json files in `publish-vX.Y.Z\` (they come from `src/AmdNr.App/config.json`
and from `payload/`). Since the installer ships before the payload, after `publish-payload.ps1` copy
`payload/payload.json` into that folder again and only then compress, so the archive that goes along
has the new components. The updater only swaps the exe, so anyone who already has the folder keeps its
json files.

The v0.4.0 `.7z` was assembled by hand with the json files and the `LEIA-ME.txt` from the 2026-09-15 beta. `config.json`
points to HF, so online it reads the current manifest; the `payload.json` in it (without `optiscaler`)
would only be used without internet.
